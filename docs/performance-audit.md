# Android performance audit

Date: 2026-09-05. Source baseline: `ba239d8`.

## Scope and evidence

Reviewed React Native rendering, filtering, analytics, storage, native SMS/Room,
logging, widgets, Play Core, and the CI/build/release workflows. Applied the
React Native performance, Kotlin concurrency/Flow, Kotlin API design, and GitHub
workflow skills. Native UI here uses Views/RemoteViews, not Jetpack Compose.

This is a source/log audit, **not an on-device benchmark**. No ADB commands,
emulator interactions, expense mutations, workflow dispatches, or releases were
performed. Python ML tooling remains excluded. Native inference call placement
was inspected, but no model or training changes were made.

Evidence includes the failed GitHub job and successful retry, generated Room and
Expo module code, synthetic calls into the actual TypeScript functions, and a
host SQLite query-plan probe. Operation counts below are not Android timings or
promised speedups. Priorities describe recommended implementation order.

This section records the original audit baseline. The subsequently authorized
implementation and its remaining validation limits are recorded in
[performance implementation](performance-implementation.md); line references and
operation counts below refer to the baseline, not the refactored source.

## Highest-priority findings

### 1. SMS batch writes are not actually enclosed in a Room transaction

**Priority: high. Confirmed from generated code.**

- `modules/expense-buddy-sms-module/android/src/main/java/expo/modules/expensebuddysmsmodule/db/SmsReviewQueueDatabase.kt:22`
  annotates ordinary database methods with `@Transaction`.
- `SmsReviewQueueDatabase_Impl.java` generated by Room overrides database plumbing
  and DAO accessors, **not** `upsertItems`, `approveItem`, `rejectItem`, or
  `dismissItem`. Those annotations do not provide a transaction wrapper here.
- Generated DAO writes individually call `DBUtil.performSuspending` with a
  transaction, so a batch still pays for individual queue/journal write
  transactions. Queue changes can also trigger repeated observer queries.
- `ExpenseBuddySmsModule.kt:297-340` loops over single-item repository operations
  for bulk approve/reject/dismiss. It has no outer transaction either.

**Recommendation:** use an explicit suspending `db.withTransaction` boundary for
each logical batch, or move transactional orchestration to an appropriately
processed DAO. Retain fingerprint uniqueness and the journal in the same
transaction. Do not parallelize writes to the same database. Add a rollback test
that fails midway through queue/journal writes, plus batch invalidation tests;
existing happy-path tests do not establish atomicity.

This is also a correctness issue: a queue status and its journal record can be
committed independently today.

### 2. SMS work blocks Expo's shared async-function queue

**Priority: high. Confirmed execution path; latency needs device measurement.**

- `ExpenseBuddySmsModule.kt:94-242` queries the inbox, parses messages, and runs
  classification directly inside a regular `AsyncFunction` body.
- Its database APIs use `runBlocking(Dispatchers.IO)`, as do log exports in
  `modules/expense-buddy-logger/android/src/main/java/expo/modules/expensebuddylogger/ExpenseBuddyLoggerModule.kt:28-45`.
- Installed Expo source dispatches regular async functions onto
  `AppContext.modulesQueue`, backed by **one HandlerThread**. Moving the inner
  work to IO with `runBlocking` still occupies that thread while waiting.
- `moduleScope.cancel()` only cancels the separately launched queue observer;
  it does not make these blocking bodies cancellation-aware.

**Recommendation:** use Expo's supported suspending async-function API, move
blocking ContentResolver work to IO and CPU parsing/inference to an appropriate
dispatcher, and suspend for Room calls. Preserve the scan's single-flight guard,
module/context lifetime, and failure behavior. Add cooperative cancellation or
ContentResolver cancellation at the actual work boundary. Do not claim this is
currently blocking Android's main thread: it blocks the **Expo module queue**.

Separately, `ExpenseBuddySmsReceiver.kt:33-45` parses incoming SMS before
`goAsync()`, on the receiver callback thread. Move parsing inside the bounded
background operation; its existing timeout currently covers database/notification
work but not parsing.

### 3. SMS review mounts every card and its animations

**Priority: high for populated queues. Confirmed rendering shape.**

`components/ui/SmsImportReviewScreen.tsx:579,808-917` puts all pending items in a
`KeyboardAwareScrollView` using `.map()`. Each row includes several labels,
five buttons, callbacks, and entering/exiting/layout animations. The pending
Room query is unbounded: the 500-message scan cap is not a total queue cap.
Expanding one SMS also rerenders this large parent tree.

**Recommendation:** use the existing FlashList dependency for the review list,
extract a memoized row with stable item/action props, and keep the editor's
keyboard-aware form separate. Apply layout animation only where it helps visible
items. Preserve confirmations, selection, scrolling, and large-text behavior.
Measure opening, expanding, scrolling, and bulk removal with 50/250/500 items.

## Other actionable runtime findings

### 4. Native queue observation reads more than it uses

**Priority: medium; address alongside batching.**

`ExpenseBuddySmsModule.kt:48-54` collects an entire
`Flow<List<ReviewQueueEntity>>` but discards its rows and sends a payload-free
event. `providers/sms-import-review-provider.tsx:48-77` then fetches the full
snapshot again. The JS 300ms debounce does not remove native query work that has
already happened.

Use a lightweight invalidation/revision signal rather than hydrating all SMS
bodies for a notification. Do not replace it with only a distinct pending count:
same-count edits also need to refresh. Make refresh coalescing retain a pending
invalidation while a fetch is in flight; the current `isFetchingRef` early return
can discard that trailing refresh. Keep the native queue as source of truth.

The query in `db/ReviewQueueDao.kt:11-15` filters by status and sorts by timestamp,
but `db/ReviewQueueEntity.kt:9-12` declares separate indices. A host SQLite probe
of that schema reports `USE TEMP B-TREE FOR ORDER BY`; a `(status, timestamp)`
index removes it. Validate with Room/Android query plans and a non-destructive
migration. Reassess the separate fingerprint index: the primary key already
provides uniqueness/indexing.

### 5. Widgets repeatedly load and process the full ledger

**Priority: medium, increasing with ledger size and widget count.**

`modules/expense-buddy-widget/android/src/main/java/expo/modules/expensebuddywidget/ExpenseWidgetStore.kt:29-90`
loads every indexed expense, parses JSON/dates, scans for each of seven days,
and sorts all matching rows to retain eight recent entries. This happens even
for Summary, which needs only totals/counts. Each widget instance calls `read`
independently. Recent does it in both `RecentWidgetProvider` and
`RecentWidgetService.Factory.onDataSetChanged`.

Reuse a live parsed snapshot within a coordinated refresh and derive needed
results in one pass; use a bounded top-eight selection instead of sorting the
whole ledger for Recent. Coalesce overlapping resize/update work per widget and
bound its lifetime. Preserve ADR-012: widgets must still read live native data
when JS is absent. Do not add a long-lived cache keyed only by `max(updatedAt)`:
deletes, settings, time, and timezone changes also matter.

### 6. Analytics has avoidable per-expense work and intermediate data

**Priority: medium. Confirmed synthetic operation counts.**

- `utils/analytics/filters.ts:202-233,282-288`: a rolling filter recomputes
  `now`, day boundaries, and the window lookup for every expense. A synthetic
  10,000-row `1y` filter performed **10,000 no-argument Date constructions**.
  Compute one range per call and compare each parsed date against it. Preserve
  local-day/DST semantics and all existing filter rules.
- `utils/analytics/aggregations.ts:197-208` calls a resolver that linearly searches
  payment instruments for each expense. A 10,000-row fixture with 20 instruments,
  all referencing the last instrument, made **220,020 instrument ID property
  reads**, including resolution/output reads. Build an ID map once, as the main
  filtering path already does.
- `aggregateByDay` (`aggregations.ts:254-289`) generates/formats every daily point
  before `utils/analytics/spending-trend.ts:16-51` parses and groups them into
  weekly/monthly points. A ten-year range created **3,653 daily intermediates**
  for **121 monthly points**. Select granularity early and aggregate directly
  into zero-filled buckets, preserving partial-period labels and exact totals.

`useDeferredValue` changes scheduling; it does not move a long synchronous
filter/sort off the JS thread or make the function itself interruptible.

### 7. Logging has an unbounded work queue and expensive steady-state pruning

**Priority: medium, especially during scans and bulk actions.**

`modules/expense-buddy-logger/android/src/main/java/expo/modules/expensebuddylogger/LoggerApi.kt:20-30,74-98`
launches one coroutine per log entry. At capacity, sustained logging repeatedly
does insert/count/prune work. The stored-row cap does not bound queued coroutines.
Initialization also replaces the scope without stopping its predecessor.

Use one explicitly owned, bounded writer that batches inserts and prunes once
per batch or at a high-water threshold. Define overflow behavior by severity,
make initialization idempotent, and retain the local-only diagnostic contract.
Test a saturated buffer and repeated initialization, not only a few inserts.

### 8. The scan cursor tracks parsed transactions, not scanned messages

**Priority: medium; correctness-sensitive.**

`ExpenseBuddySmsModule.kt:158-170,222-229` derives the cursor from parsed results.
`SmsInboxScanner.kt:34-42` drops non-matches before returning. When no transaction
matches, the cursor advances only one millisecond past the lower bound, allowing
the same non-transaction SMS to be queried/parsed repeatedly within the lookback.

Return explicit scan progress separately from parsed candidates. Design paging
and the timestamp/message-ID tie-break together: simply advancing to the newest
message in a descending 500-item page could skip older, unprocessed messages.
Test empty matches, more than 500 messages, and equal timestamps before changing
the watermark. Do not trade scan speed for dropped import candidates.

### 9. Widget periodic work survives removal of the last widget

**Priority: low-to-medium battery housekeeping. Confirmed lifecycle omission.**

`WidgetRefreshWorker.kt:26-35` schedules unique 30-minute periodic work.
`WidgetProviderBase.kt` has `onEnabled` but no cancellation on last-widget removal.
The worker then continues waking just to discover there are no widgets.

Cancel only after checking all three provider kinds have no remaining instances;
removing the last Summary must not cancel a remaining Trend/Recent widget. Keep
the 30-minute backstop for installed widgets and test removal/re-addition.

## Lower-confidence candidates: profile before changing

- `stores/hooks/use-expenses.ts:10-23` subscribes every caller to the expense
  array and derives active expenses even for callers using only actions. Narrow
  subscriptions/action hooks could reduce save-time work. The existing shared
  `DerivedExpenseDataProvider` already avoids repeating currency/month derivation;
  preserve it rather than introducing duplicate caches.
- `services/storage.ts:104-121` uses synchronous MMKV loops despite an async API;
  `services/expense-storage.ts:33-57` parses the whole ledger at startup. Profile
  large-ledger startup/import before introducing chunking, which needs coherent
  snapshots and crash-safe persistence.
- `app/_layout.tsx:66-71` runtime-loads two bundled fonts. Native embedding through
  `expo-font` may reduce startup work, but confirm family/weight mapping and theme
  splash behavior. Do not remove the theme splash gate to improve a stopwatch.
- Release minification/resource shrinking are off in the generated Gradle
  defaults. Evaluate R8 separately for APK size/runtime benefits; it may increase
  build memory and requires widget/Expo/Room/LiteRT release smoke tests.

## GitHub build failure: diagnosis and free-runner plan

Failed job: [101264692024, attempt 1](https://github.com/sudokoi/expense-buddy/actions/runs/33950331207/job/101264692024).
Run commit: `602d685adc8afee74516b2e85f3771ddf0519611`.

- Attempt 1: `java.lang.OutOfMemoryError: Java heap space`, followed by
  `:app:l8DexDesugarLibRelease FAILED`; Gradle failed after 7m47s. The Gradle cache
  missed, and 589 actionable tasks were executed before failure.
- Attempt 2: successful after 9m27s of Gradle work, but warned that the daemon
  had exhausted **Metaspace**. It reported **2 GiB maximum heap / 512 MiB maximum
  Metaspace**. The Gradle cache hit, yet all 922 actionable tasks were executed.
- This establishes JVM heap pressure in the failure and a second Metaspace
  capacity problem in the retry. It does **not** establish host-RAM exhaustion,
  a Kotlin compiler leak, or that a warm cache alone fixes the failure.

The repository is public and uses `ubuntu-latest`. GitHub currently documents
the standard/free public Linux runner as **4 CPUs / 16 GB RAM**. No hardware
upgrade is proposed. Record `nproc`, `free -h`, and available disk in each run
rather than assuming the resource envelope forever.

### Proposed bounded starting configuration, not yet validated in CI

```properties
org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8
org.gradle.workers.max=2
org.gradle.parallel=false
org.gradle.caching=true
kotlin.daemon.jvmargs=-Xmx1g -XX:MaxMetaspaceSize=512m
```

This gives the failing JVM more headroom while reducing simultaneous work.
Heap limits are not total process-RAM limits; native tooling, JVM overhead,
Node/Metro, and the OS still need room. Measure peak process-tree RSS and total
available memory. Tune worker count/parallelism back upward only after cold and
warm builds are reliable. Do not use `JAVA_TOOL_OPTIONS` to give every JVM 4 GB,
add unlimited swap, or disable desugaring to hide this failure. The two matrix
profiles run on separate VMs; `max-parallel: 1` would not reduce per-VM memory.

`android/` is generated/untracked here and EAS local builds use a temporary
project. Put the policy in a tracked Expo config plugin, or explicitly provision
the inherited Gradle user-home properties before EAS. Verify the effective
properties inside the generated build. Editing only this checkout's ignored
`android/gradle.properties` would not repair GitHub builds.

### Workflow optimization/reliability follow-ups

1. `.github/workflows/release-local.yml:72-80`: the cache key omits `yarn.lock`,
   Node version, Expo app/plugin configuration, and EAS inputs that change the
   generated native build. Give task caching an explicit policy and use a
   toolchain/dependency-aware key with controlled restore keys. Keep one owner
   for Gradle caching; do not stack competing cache actions. A dependency cache
   hit is not evidence of task-output reuse.
2. Preserve diagnostics on failure: Gradle daemon logs, local profile reports,
   effective memory settings, and sampled process-tree memory. EAS currently
   points at reports inside its disposable build directory. Use a controlled
   temporary build path/cleanup policy and upload only selected diagnostics,
   never the entire build workspace or signing credentials. Automatic public
   heap-dump uploads are inappropriate.
3. `.github/workflows/ci.yml` omits `yarn typecheck` and Expo dependency checks.
   Add them as release gates. Its native test script can prebuild and execute a
   full debug unit-test graph, but CI has no explicit Java/Android setup or
   Gradle cache and only a 10-minute timeout. Align its toolchain and resource
   policy with builds; consider named native-module test tasks after verifying
   complete module coverage. Do not remove native tests to save time.
4. APK/AAB files are already compressed: use `compression-level: 0` for artifact
   upload and download only the internal APK in the GitHub release job instead
   of both profiles. Keep the production AAB for Play submission.
5. `release-local.yml:203-254` and `release.yml:189-240` submit to Play production
   after successful builds, including manual dispatches with arbitrary suffixes.
   Explicit submission intent/environment approval would make build-only
   validation safer. Do not dispatch these workflows merely to benchmark them.
6. `eas-version: latest` lets retry tooling drift independently of the lockfile.
   Consider a tested EAS CLI version with deliberate updates for reproducible
   memory comparisons. Keep `.node-version` and Java 17; changing the JDK is not
   the diagnosed memory fix.

## Suggested execution order

1. Free-runner build memory/diagnostics policy, with cold/warm build-only checks.
2. Real Room transactions and coroutine-based Expo APIs; verify rollback,
   cancellation, duplicate handling, and a single coherent batch refresh.
3. Virtualized SMS review plus lighter queue invalidation/querying.
4. Filter/instrument/trend work reduction, followed by native widget/log batching.
5. Profile release-mode startup, frame times, memory, and background wakeups on a
   representative device when ADB is available. Use synthetic ledgers and queues,
   not the user's stored expense data. Revisit lower-confidence candidates only
   after tracing identifies their cost.

Already useful and worth retaining: History's FlashList/memoized rows, cached
Intl formatters, shared currency/month derivation, bounded recent-widget output,
native parser ownership, Play Core listener teardown, and arm64-only builds.
